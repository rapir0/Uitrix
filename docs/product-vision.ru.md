# Uitrix CRM — Product Vision / Видение продукта

> **Версия:** 1.1
> **Статус:** Draft
> **Дата:** 2026-11-07
> **Владелец:** rapir0

## 0. Краткое описание

Uitrix CRM — self-hosted система управления заявками (тикетами) для команд аутсорс-технической поддержки. Основной интерфейс — канбан-доска со статусами, интегрированная с Telegram-ботом, через который клиенты создают заявки. Система хранит контрагентов, их подразделения и контакты, обеспечивает полный цикл обработки заявки: от поступления до закрытия, с передачей между специалистами и аудитом всех действий.

**Ключевая идея:** техподдержка, которая начинается в Telegram (где клиенты и так сидят) и превращается в структурированный процесс в веб-интерфейсе — без дорогих подписок Zendesk/Freshdesk и с полным контролем над данными.

## 1. Проблема и целевая аудитория

**Проблема.** Небольшие аутсорс-команды техподдержки (2–20 человек) ведут заявки в мессенджерах, Excel и Trello-подобных досках. Это приводит к:
- потерянным заявкам и «забытым» клиентам;
- отсутствию единой истории по контрагенту;
- невозможности оценить загрузку команды;
- ручной передаче задач и, как следствие, задержкам.

Zendesk, Freshdesk, Jira Service Management дороги ($15–50 за агента в месяц), не заточены под Telegram-первый сценарий и не работают в self-hosted.

**Целевая аудитория.**
- Аутсорс-команды техподдержки малого и среднего бизнеса (2–20 агентов).
- Клиенты этих команд (контрагенты) — компании, у которых есть сотрудники, обращающиеся в поддержку через Telegram.
- Роли в команде-покупателе Uitrix: владелец, тимлид/админ, агент.

**Кому НЕ подходит.** Enterprise с сотнями агентов (нужна multi-tenancy и SLA-движок), команды без Telegram, команды, которым нужны телефония и звонки.

## 2. Глоссарий

| Термин | Определение |
|---|---|
| **Тикет** (заявка, ticket) | Единица работы: обращение клиента, требующее действия агента. |
| **Контрагент** (contractor) | Компания-клиент, за которой закреплены её контакты и подразделения. |
| **Подразделение** (department) | Структурная единица контрагента (филиал, отдел). Контакт может быть привязан к подразделению. |
| **Контакт контрагента** (contact) | Физическое лицо со стороны клиента (ФИО, @username Telegram, телефон). В CRM не логинится. Инициатор тикета. |
| **Пользователь CRM** (user, агент, админ) | Сотрудник команды-владельца Uitrix. Логинится в веб-интерфейс. Берёт тикеты в работу. |
| **Агент** | Пользователь CRM с ролью `agent`. Видит и обрабатывает тикеты. |
| **Администратор** | Пользователь CRM с ролью `admin`. Управляет пользователями, контрагентами, статусами. |
| **Статус** | Состояние тикета в жизненном цикле (Новая, В работе, …). Соответствует столбцу канбана. |
| **Подстатус** | Уточнение статуса (например, «На паузе» → «Ожидание клиента»). |
| **Вложение** (attachment) | Файл (фото, документ), приложенный к тикету. |

## 3. Технологический стек и архитектура

**Высокоуровневая схема:**
```
[Telegram Bot] ←→ [Backend API] ←→ [PostgreSQL]
                       ↑
                  [Nginx + TLS]
                       ↑
                   [Browser]
```

**Стек:**
- **Backend:** Python 3.12 + FastAPI, SQLAlchemy 2 (async), Alembic для миграций.
- **БД:** PostgreSQL 16. Резервное копирование — ежедневный `pg_dump` по cron + ротация 14 дней + ежемесячная проверка восстановления.
- **Frontend (веб-интерфейс):** server-side rendering на Jinja2 + Bootstrap 5 + htmx + Alpine.js. Drag & Drop на канбане — SortableJS. Без отдельного SPA-билда — проще деплой, меньше инфраструктуры.
- **Reverse-proxy:** Nginx с TLS (Let's Encrypt). Backend-порт 8000 не выставляется наружу, доступен только через Nginx.
- **Telegram Bot:** python-telegram-bot (v21+), режим webhook на проде, polling — локально для разработки.
- **Вложения:** локальная директория `/var/uitrix/uploads/` (с миграцией на S3/MinIO при росте). Отдача — через backend с проверкой прав.
- **Контейнеризация:** Docker + Docker Compose (локально и на проде). Сервисы: `backend`, `db`, `bot`, `nginx`, `cron` (бэкапы).

## 4. Веб-интерфейс

### 4.1. Первый вход

При первом запуске создаётся пользователь-администратор из переменных окружения `ADMIN_USERNAME` (по умолчанию `uitlocal`) и `ADMIN_INITIAL_PASSWORD` (задаётся в `.env`, **не хранится в репозитории**).

При первом входе пользователь обязан сменить пароль — до этого доступны только форма смены пароля и выход.

### 4.2. Вкладка «Канбан» (основное окно)

- Столбцы — статусы тикетов.
- Тикеты в столбце сортируются по `created_at`, направление переключаемое (новые сверху / старые сверху). Настройка сохраняется per-user.
- Карточка тикета — стиль «стикер»:
  - **Строка 1:** название контрагента; фон затемнён относительно тела карточки.
  - **Строка 2:** инициатор — ФИО или `@username` Telegram.
  - **Тело:** текст тикета (обрезается до 4–5 строк с «…»).
  - **Низ:** дата и время создания в формате `DD.MM.YYYY HH:MM`.
- Drag & Drop между столбцами меняет статус. Порядок внутри столбца определяется сортировкой, не ручной перестановкой. **В MVP перетаскивание меняет только статус, не позицию.**
- Клик по карточке — модальное окно:
  - полный текст, вложения, история изменений;
  - редактирование (статус, подстатус, ответственный, контрагент, подразделение, текст);
  - передача другому агенту;
  - закрытие (перевод в «Выполнена» / «Не выполнена»).
- Кнопка «+» — создание тикета вручную (см. раздел 7.1).
- Фильтры над доской: «Мои тикеты» (toggle), «Контрагент», «Статус» (для скрытия пустых столбцов), «Период».

### 4.3. Вкладка «Контрагенты»

Список контрагентов с поиском по названию и ИНН. Клик по строке — карточка контрагента.

Иконки-действия в строке:
- ✏️ **Реквизиты** — редактирование полей;
- 🏠 **Подразделения** — список подразделений контрагента (CRUD);
- 👤 **Контакты** — список контактов контрагента с указанием подразделения.

**Поля контрагента:** название, ИНН, сайт, общий телефон, адрес, список подразделений (название + адрес), флаг «Абонентский договор».

### 4.4. Вкладка «Сотрудники» (контакты контрагентов)

Список **контактов контрагентов** — людей со стороны клиента, обращающихся в поддержку. Это не пользователи CRM, они не логинятся.

Отображаемые поля: ФИО, `@username` Telegram, телефон, контрагент, подразделение, число открытых тикетов.

Фильтры:
- по контрагенту (dropdown);
- по подразделению (dropdown);
- по ФИО / `@username` — текстовый поиск;
- чекбокс «Есть открытые тикеты».

### 4.5. Вкладка «Пользователи CRM» (только для admin)

Доступна только роли `admin`.

Список пользователей CRM: ФИО, email, `@username` Telegram, роль, статус (активен/заблокирован), дата последнего входа.

Действия: создать, отредактировать, деактивировать, сбросить пароль.

### 4.6. Вкладка «Настройки»

**Личные настройки (все роли):**
- отображать в интерфейсе ФИО или `@username` Telegram;
- показывать/скрывать аватар из Telegram (best-effort);
- язык интерфейса (пока только русский);
- тема (светлая / тёмная / системная).

**Системные настройки (только admin):**
- управление статусами и подстатусами (см. раздел 5);
- настройки Telegram-бота (токен, режим: polling/webhook, приветственное сообщение);
- параметры резервного копирования.

**Про аватары из Telegram.** Забираются через `getUserProfilePhotos`, только если пользователь явно взаимодействовал с ботом и фото доступно. API не гарантирует наличие фото; при отсутствии — инициалы в кружке. Опциональная фича, не блокер.

### 4.7. Вкладка «Отчёты» (только admin)

Минимальный набор отчётов для MVP:
- **За сегодня** — создано / закрыто / передано / в работе / без ответственного;
- **За период** — сводка по агентам (сколько тикетов взято и закрыто);
- **По контрагентам** — топ-10 по количеству открытых тикетов.

## 5. Статусы и подстатусы

**Базовые статусы (seed при первом запуске):**

| Статус | Тип | Подстатусы по умолчанию |
|---|---|---|
| Новая | открытый | — |
| В работе | открытый | — |
| На паузе | открытый | Отложена клиентом, Ожидание техподдержки, Ожидание сторонней организации |
| Передача коллеге | открытый | — |
| Выполнена | закрытый | — |
| Не выполнена | закрытый | Не актуально, Не согласовано, Нет реакции клиента |

**Правила:**
- Статусы и подстатусы создаются и редактируются в веб-интерфейсе (только admin).
- Удаление статуса — **soft-delete**: `is_archived = true`. Столбец скрывается с доски, но тикеты в нём остаются. При попытке удалить непустой статус админ получает предупреждение с количеством тикетов и выбор: (a) архивировать вместе с тикетами, (b) сначала перенести тикеты в другой статус, (c) отменить.
- У каждого статуса — цвет (для визуального различения на доске).
- Атрибуты статуса: `is_closed` (закрывающий), `is_default` (для новых тикетов — «Новая»), `position` (порядок столбцов).
- Подстатусы выбираются после статуса в боте и в вебе.
- Тикеты создаются/закрываются/редактируются/передаются как в боте, так и в вебе.

## 6. Telegram-бот

### 6.1. Сценарии взаимодействия

**6.1.1. Создание тикета через бота**

1. Клиент нажимает «➕ Создать» **или** пересылает боту сообщение от клиента с заявкой.
2. Если по кнопке — бот спрашивает текст тикета. Можно ввести вручную, можно переслать сообщение — пересланное станет текстом.
3. Если сообщение переслано из другого чата — бот запоминает `telegram_id` инициатора и его `@username`/ФИО (best-effort).
4. Если аккаунт скрыт или текст введён вручную — бот запрашивает ФИО клиента и телефон (или `@username`).
5. **Привязка к контрагенту:**
   - если `telegram_id` уже известен — берётся закреплённый контрагент и (если был) подразделение;
   - если нет — бот спрашивает контрагента из списка (inline-кнопки) и подразделение (опционально);
   - создаётся новый контакт контрагента с этим `telegram_id`.
6. Бот спрашивает статус (по умолчанию — «Новая», можно сразу указать другой).
7. Тикет создаётся, клиент получает подтверждение с номером тикета.

**6.1.2. Уведомления клиенту**

- При смене статуса тикета клиенту приходит уведомление в тот же чат с ботом: «Тикет #123 переведён в статус "В работе"».
- Уведомления можно отключить командой `/mute` (per-contact настройка).

**6.1.3. Просмотр статуса**

- Команда `/status` — список активных тикетов клиента с текущими статусами.

**6.1.4. Вложения**

- При создании тикета (или позже) клиент может отправить фото, документ, голосовое сообщение.
- Файлы сохраняются в `/var/uitrix/uploads/{ticket_id}/{uuid}.{ext}`.
- Метаданные (тип, размер, имя) — в БД.
- Лимит одного файла: 20 МБ (стандарт Telegram). Лимит вложений на тикет: 10.

### 6.2. Режим работы

- **Dev:** polling (long-polling). Публичный URL не нужен.
- **Prod:** webhook. URL: `https://crm.ghostnode.ru/telegram/webhook/{secret}`. Секрет — в `.env`, проверяется на входе. Отдаётся через Nginx с TLS.

### 6.3. Привязка контактов

Открытый вопрос — как избежать дублей, если один человек пишет с двух аккаунтов или пересылает чужие сообщения. Для MVP:
- **Один `telegram_id` = один контакт.** Дубликаты по ФИО/телефону возможны.
- В веб-интерфейсе админ может **слить** два контакта в один (перенос всех тикетов).
- Раздел «возможные дубликаты» в админке — post-MVP.

## 7. Процессы

### 7.1. Создание тикета

**Через бота:** см. раздел 6.1.1.

**Через веб:** кнопка «+» на канбане → модальное окно с полями:
- контрагент (dropdown с поиском) — обязательно;
- подразделение (dropdown, зависит от контрагента) — опционально;
- контакт (dropdown с поиском по ФИО/username) или создать нового — обязательно;
- текст тикета — обязательно;
- вложения — опционально;
- статус (по умолчанию «Новая») и подстатус;
- ответственный (по умолчанию — текущий пользователь).

### 7.2. Передача тикета

- В карточке тикета или через drag & drop в статус «Передача коллеге».
- Модальное окно: выбор агента (dropdown только активных пользователей с ролью `agent` или `admin`), комментарий (опционально), кнопка «Передать».
- После передачи: `assignee_user_id` меняется, статус → «Передача коллеге», новый ответственный получает уведомление **в Telegram** (не в CRM) через бота.
- История передач сохраняется в `audit_log`.

### 7.3. «Мои тикеты»

- Toggle «Мои тикеты» на канбане — фильтр `assignee_user_id = current_user.id` (опционально — плюс тикеты без ответственного).
- Отдельная страница `/my-tickets` — список открытых тикетов пользователя. В MVP — «желательно», а не обязательно.

### 7.4. Отчёт за сегодня

Автоматически формируется при открытии раздела «Отчёты». Показывает за текущий день (с 00:00 по часовому поясу сервера):
- создано тикетов: N;
- закрыто (Выполнена + Не выполнена): M;
- передано: K;
- в работе сейчас: P;
- без ответственного: Q.

Админ может выгрузить в CSV (post-MVP).

## 8. Роли и права

| Действие | admin | agent |
|---|---|---|
| Просматривать канбан | ✅ | ✅ |
| Создавать тикет | ✅ | ✅ |
| Редактировать чужой тикет | ✅ | ✅ (с записью в аудит) |
| Брать тикет в работу | ✅ | ✅ |
| Передавать тикет | ✅ | ✅ |
| Удалять тикет | ✅ | ❌ |
| Управлять контрагентами | ✅ | ⚠️ создавать/редактировать — да, удалять — нет |
| Управлять пользователями CRM | ✅ | ❌ |
| Управлять статусами | ✅ | ❌ |
| Просматривать отчёты | ✅ | ⚠️ только свои |
| Настройки системы | ✅ | ❌ |

Роль `viewer` (только чтение) — **вне MVP**.

## 9. Регистрация и управление пользователями

- **Самостоятельная регистрация отсутствует.** Пользователей создаёт только admin.
- Создание пользователя: админ вводит ФИО, email, `@username` Telegram, роль; генерирует одноразовую ссылку-приглашение (срок 24 часа) или задаёт временный пароль.
- При первом входе — принудительная смена пароля.
- Деактивация — вместо удаления (сохраняет историю тикетов и аудит).
- Восстановление пароля — через админа (MVP) или email-ссылку (post-MVP).

## 10. Схема данных (высокоуровнево)

Точные поля и типы — в миграциях Alembic.

```
users (пользователи CRM)
  ├── id, username, email, full_name, telegram_username,
  │   password_hash, role, is_active, must_change_password,
  │   created_at, last_login_at

contractors (контрагенты)
  ├── id, name, inn, website, phone, address,
  │   has_service_contract, created_at, updated_at

departments (подразделения)
  ├── id, contractor_id → contractors.id, name, address

contacts (контакты контрагентов)
  ├── id, contractor_id → contractors.id, department_id → departments.id,
  │   full_name, telegram_id (unique), telegram_username, phone,
  │   created_at, updated_at

ticket_statuses
  ├── id, name, color, is_closed, is_default, position, is_archived

ticket_substatuses
  ├── id, status_id → ticket_statuses.id, name, position, is_archived

tickets
  ├── id, number (auto-increment), contractor_id, department_id,
  │   contact_id, assignee_user_id (nullable), status_id, substatus_id (nullable),
  │   body (text),
  │   created_by_user_id (nullable, если через веб) / created_via ('bot'|'web'),
  │   created_at, updated_at, closed_at

attachments
  ├── id, ticket_id → tickets.id, filename, path, size, mime_type,
  │   uploaded_by_contact_id (nullable) / uploaded_by_user_id (nullable),
  │   created_at

audit_log
  ├── id, entity_type ('ticket'|'user'|'contractor'|…), entity_id,
  │   user_id (nullable), action ('create'|'update'|'delete'|'assign'|…),
  │   diff (JSONB), created_at
```

Индексы: `tickets(status_id, created_at DESC)`, `tickets(assignee_user_id)`, `contacts(telegram_id)`, `audit_log(entity_type, entity_id)`.

## 11. Нефункциональные требования

### 11.1. Безопасность

- Все пароли — bcrypt (или Argon2id).
- Все секреты (admin password, Telegram bot token, webhook secret, DB password) — только в `.env`, **никогда** в git.
- HTTPS везде (Let's Encrypt + Nginx).
- Rate-limit на `/login` (10 попыток/минуту с IP).
- Session — HttpOnly + Secure cookies, TTL 7 дней.
- Загрузка файлов: проверка MIME-типа, лимит размера, отдача только авторизованным пользователям.
- Backend-порт 8000 не выставлен наружу — только через Nginx.

### 11.2. Резервное копирование

- Ежедневный `pg_dump` в 03:00 по cron → `/var/backups/uitrix/db-YYYY-MM-DD.sql.gz`.
- Хранение 14 дней, ротация автоматическая.
- Вложения — rsync в `/var/backups/uitrix/uploads/` ежедневно.
- Ежемесячно — тест восстановления на чистой БД (в первый месяц вручную, потом автоматизировать).

### 11.3. Аудит и логи

- Все изменения сущностей (тикеты, контрагенты, пользователи) — в `audit_log`.
- Логи приложения — структурированные JSON, уровень INFO по умолчанию, ERROR со stack trace.
- Хранение логов — 30 дней.
- Логи Nginx — стандартные access/error, ротация через `logrotate`.

### 11.4. Приватность и 152-ФЗ

- В системе хранятся персональные данные (ФИО, телефоны, `@username`) клиентов контрагентов.
- Данные хранятся на сервере в РФ (требование 152-ФЗ при работе с российскими компаниями).
- Админ может выгрузить/удалить все данные по конкретному контакту (право на забвение).
- Резервные копии — шифруются (GPG) перед выгрузкой за пределы сервера (post-MVP).

## 12. Scope MVP и метрики

**MVP — что входит:**
- Веб-интерфейс: канбан, контрагенты, контакты, пользователи, статусы, базовые отчёты.
- Telegram-бот: создание тикета, вложения, уведомления о смене статуса, `/status`.
- Роли admin/agent, принудительная смена пароля, отсутствие самозаписи.
- Docker Compose деплой на Debian 12 + Nginx + TLS + бэкапы.
- Аудит базовых действий.

**Метрики успеха MVP (3 месяца после запуска):**
- 3–5 пилотных команд используют систему в ежедневной работе.
- 100+ тикетов обработано через бота.
- 0 потерянных сообщений/тикетов (каждое сообщение в бота → тикет или ответ).
- Uptime > 99% (замер по внешнему мониторингу).
- Backup/restore протестирован минимум дважды, RTO < 1 часа.

## 13. Явно вне MVP

- SPA-фронтенд (React/Vue). Если понадобится — отдельная ветка развития.
- Мобильное приложение.
- SLA-таймеры и автоподъём приоритета.
- Кастомные поля тикета.
- Multi-tenancy (одна инсталляция = одна команда).
- Интеграции с почтой, звонками, WhatsApp, VK.
- SSO / LDAP.
- Публичный API для внешних интеграций.
- Роль `viewer`.
- Продвинутая аналитика и дашборды.

## 14. Открытые вопросы (требуют решения)

1. **Привязка контакта при пересылке сообщения.** Если клиент A пересылает сообщение клиента B (не своего), чей `telegram_id` записывается? Решение по умолчанию: тот, кто переслал (`from.id` пересланного сообщения в Telegram API доступен не всегда). Уточнить на практике.
2. **Восстановление пароля.** Email-ссылка требует SMTP. В MVP — только через админа. Если нужна самостоятельная — нужен SMTP-провайдер.
3. **Приоритеты тикетов.** В MVP не заложены. Если понадобятся — отдельная сущность `priority` (Low/Normal/High/Urgent) + поле в тикете.
4. **Дедупликация контактов.** Слияние вручную в админке, автоматическая — post-MVP.
5. **Хранение вложений.** Локальная директория → миграция на MinIO/S3 при росте. Порог: >10 ГБ или >5000 файлов.
6. **Уведомления агентам.** В MVP — только через Telegram-бот (по `telegram_username` пользователя). Email-уведомления — post-MVP.
